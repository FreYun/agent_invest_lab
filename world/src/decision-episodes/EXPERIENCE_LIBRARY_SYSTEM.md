# 经验图书馆完整系统设计

## 1. 最终目标

经验图书馆不是把每日决策卡堆在一起，而是把大量真实决策案例，逐步沉淀为少量、有边界、可验证、可追溯的经验。

它最终应回答 Agent 三个问题：

1. 当前处境下，历史上有哪些值得检查的经验？
2. 这些经验为什么可能成立，又在什么情况下失效？
3. 它们被多少独立案例支持或反驳，目前可信到什么程度？

图书馆只提供线索、证据和质询，不替 Agent 直接下投资结论。

## 2. 两个数据库

### 决策案例库 `decision-episodes`

保存不可修改的每日 Canonical 案例，包括事实、Claim、作用机制、冲突、候选动作、最终决策和真实订单。它回答“当时发生了什么”。

### 经验图书馆 `experience-library`

保存跨案例归并后的经验卡、证据、关系、版本、馆藏快照和使用记录。它回答“从多次案例中学到了什么”。

两库物理分开。经验图书馆只引用案例 ID 和来源定位，不改写案例事实，也不与 `fund.db` 混放。

## 3. 四种核心对象

### 3.1 案例卡（Decision Episode）

一次具体日期、具体 bot 的完整决策记录，是证据源，不直接等于可复用经验。

### 3.2 经验卡（Experience Card）

跨案例稳定存在的一条机制级认识，至少包含：

- `claim`：经验主张；
- `applicable_when`：适用条件；
- `mechanism`：作用机制；
- `better_process`：建议检查或采用的决策过程；
- `invalid_when`：失效边界；
- `falsifiers`：什么证据能推翻它；
- `status`：当前等级；
- `version`：不可覆盖的版本号。

“今天 HOLD、仓位 32%”属于案例结论；“解除防御状态需要持续确认，不能由单日改善决定”才可能成为经验卡。

### 3.3 证据（Evidence）

证据记录案例对经验主张的裁决结果，只有三种：`SUPPORTS`、`REFUTES`、`UNCERTAIN`。这三个值是证据结论，不是图书馆的推理关系。

每条证据必须记录案例 ID、来源、结果可见时间、验证状态，以及 persona 和 Regime 是否独立。

连续三天处于同一段行情，不能简单算三次独立验证。

### 3.4 关系（Relations）

关系分为基础挂接边和推理边两层。

#### 基础挂接边

`INSTANTIATES` 把案例卡挂到经验卡上，表示“这个真实案例是该经验的一次实例”。它负责来源追溯和入馆，不属于下面六种推理关系。

#### 六种推理关系

每张案例卡和经验卡都可以表示为四元组：处境 S、行为 A、结果 O、机制 M。两个知识节点在四元组上的重叠方式，产生六种关系：

| 关系 | 四元组判据 | 推理价值 |
|---|---|---|
| `CORROBORATES` 佐证 | S 同、A 同、O 同 | 说明经验被再次复现 |
| `REGIME_ALERT` Regime 警报 | S 同、A 同、O 反 | 说明处境定义可能遗漏了关键变量 |
| `CONTRASTS` 对照 | S 同、A 异、O 可比 | 提供接近反事实的动作比较 |
| `GENERALIZES / SPECIALIZES` 泛化／特化 | S 异、M 同 | 从具体案例抽象上位机制，或限定更窄边界 |
| `CONFLICTS_WITH` 冲突 | S 有交集、A 相反 | 暴露互斥建议，要求寻找判别条件 |
| `DEPENDS_ON / OVERRIDES` 依赖／优先 | M₁ 依赖 M₂，或规则有明确优先级 | 在多条经验同时命中时完成仲裁 |

六种关系既可由案例与经验之间产生，也可存在于经验卡之间。例如，新案例可以佐证一张经验卡、对它触发 Regime 警报，或与其形成动作对照；两张经验卡则可以形成泛化、冲突和优先关系。

证据裁决与推理关系可以同时存在：某案例的结果可以在证据表中记为 `REFUTES`，并在关系层触发 `REGIME_ALERT`，推动经验卡收窄适用范围或产生新版本。

相似度、“处境相近”和同日 cohort 用于检索时动态计算，不为每两张卡持久化一条边。只有需要裁决、需要保留历史或无法廉价重算的关系才落库，避免关系数量爆炸。

## 4. 从案例卡到经验卡

完整流水线如下：

```text
原始 session、fund.db、订单
        ↓
规则提取事实 → Qwen 整理语义 → 程序校验
        ↓
Canonical 案例卡
        ↓
跨案例按“适用条件 + 作用机制”聚类
        ↓
生成或更新 Candidate 经验卡
        ↓
以 INSTANTIATES 挂接案例，记录支持、反驳、未决证据
        ↓
生成六种推理关系并识别冲突、对照和边界缺口
        ↓
结果成熟后重新裁决
        ↓
晋升、收窄、分裂、降级或废止
        ↓
发布带时间截面的馆藏 Snapshot
```

Qwen 负责把不同表述归并成可读候选，不负责判定事实真假、证据独立性或最终晋升。数值、来源、时间和状态均由程序校验。

不是每个 Claim 都要进入图书馆。只有具备可复用机制、明确边界和可证伪条件的 Claim 才能生成 Candidate；单日市场描述和具体仓位继续留在案例库中。

## 5. 经验卡生命周期

| 等级 | 含义 | 使用权限 |
|---|---|---|
| L0 案例观察 | 只在单个案例中出现 | 仅作来源证据 |
| L1 Candidate | 机制明确，但仍是孤证或未有结果 | 可供研究，不应直接影响仓位 |
| L2 Corroborated | 获得跨 persona、跨 Regime 的独立支持，且无重大未决反驳 | 可作为决策线索 |
| L3 Promoted | 经过反事实或隔离回测验证并由人确认 | 可进入正式决策简报 |
| Deprecated | 被反驳、被上位版本替代或边界失效 | 保留审计，不再召回 |

出现反例时不删除旧卡：可以收窄适用范围、分裂成两张卡或产生新版本。任何晋升都必须能回溯到具体案例和证据。

## 6. Agent 如何使用图书馆

在回测日期 D，系统先使用 D 时点可见的数据机械计算当前处境，包括市场、账户、信号、约束和决策类型。然后：

1. 只读取 `knowledge_cutoff <= D` 的馆藏 Snapshot；
2. 隐藏 `outcome_available_at > D` 的结果；
3. 排除同一 run、同一时期产生的自我泄漏经验；
4. 给 Agent 少量起始经验卡，并说明匹配原因、证据强度和失效边界；
5. Agent 可沿反驳、冲突、上位规则等关系继续查阅，而不是照抄相似案例；
6. Agent 必须对每张卡标注“适用、不适用、存疑”，并说明是否改变了决策。

这次使用记录会成为图书馆的审计数据，但只有未来结果成熟后，才能转成新的支持或反驳证据。

## 7. 一个实际归并示例

2026-08-06、08-07、08-10 三张 Canonical 案例都出现了：防御 Regime 尚未解除、多套指标存在差异、确认窗口未完成，因此保持 HOLD。

它们可以共同产生一张 Candidate：

> 防御 Regime 的解除不能由单日改善决定；当确认窗口未完成、多引擎尚未收敛且账户风险较高时，应维持原状态。

三张日卡作为来源证据挂在这张经验卡下面。但因为它们属于同一段连续行情，初始只能视为一个 Regime 证据，不能立即晋升为普遍规律。以后不同 bot、不同市场阶段产生的支持或反例，再推动它晋升或收窄。

## 8. 最小数据结构

经验图书馆至少需要以下表：

- `experience_cards`：经验卡当前身份与状态；
- `experience_card_versions`：所有历史版本；
- `case_experience_edges`：案例通过 `INSTANTIATES` 挂接经验卡；
- `card_evidence`：案例对经验的 `SUPPORTS / REFUTES / UNCERTAIN` 裁决；
- `reasoning_relations`：六种类型化推理关系及其判据、有效期和裁决记录；
- `situation_index`：适用条件的结构化索引；
- `library_snapshots`：指定时间点可使用的馆藏；
- `snapshot_cards`：每个 Snapshot 包含的卡与版本；
- `usage_logs`：Agent 查阅、判断和决策影响记录；
- `adjudication_logs`：晋升、降级、分裂及人工审批记录。

## 9. 建成标准

满足以下条件，才算建成经验图书馆：

- 每张正式经验卡都能追溯到 Canonical 案例和原始证据；
- 案例、经验和结果三者分层，不把后验结果写回当时事实；
- 经验有明确的适用条件、作用机制和失效边界；
- 支持与反驳同时保存，证据独立性不会被重复日期夸大；
- 所有变更通过新版本和裁决日志完成；
- 任意回测日期都能重建当时真实可见的馆藏；
- Agent 只收到少量相关线索，并可继续沿关系查证；
- 每次使用都可回放：看到了什么、为什么采用、是否改变决策。

一句话概括：**案例库保存历史，经验卡归纳机制，证据负责审判，关系支持推理，Snapshot 保证时间正确，使用记录让图书馆持续进化。**

## 10. 效用边界与验证方法

### 10.1 它能帮助泛化，但不自动产生泛化

经验图书馆是 Agent 的外部记忆和推理脚手架，不会改变模型参数。它能让 Agent 在一次决策中取得相关经验、反例和对照，但不能保证 Agent 已经真正学会某条规律。

六种关系提供的是推理语法：

- `CORROBORATES`：检查假设是否被复现；
- `REGIME_ALERT`：发现相同动作产生相反结果时遗漏的变量；
- `CONTRASTS`：比较同类处境中的不同动作；
- `GENERALIZES / SPECIALIZES`：在具体案例与一般机制之间切换；
- `CONFLICTS_WITH`：避免只沿单一结论思考；
- `DEPENDS_ON / OVERRIDES`：处理条件依赖和规则冲突。

是否形成有效泛化，主要取决于关系是否建对、证据是否独立，以及 Agent 是否真正检查了关键差异。错误的机制归并会产生错误泛化；只提供支持案例会把图书馆变成确认偏误放大器。

因此，每次召回至少应同时提供：匹配经验、一个反例或冲突经验、适用边界，以及“当前处境与来源案例最重要的不同点”。Agent 必须说明采用或拒绝经验的理由，不能只复述卡片结论。

### 10.2 对投资最可能产生的价值

图书馆首先应改善决策过程，而不是直接承诺产生 Alpha。最可期待的效果包括：

- 减少重复性决策错误和规则违规；
- 降低无必要的往返交易和换手成本；
- 改善回撤控制和极端行情下的应对；
- 提高不同日期、不同 bot 之间的决策一致性；
- 让错误发生后可以定位到具体经验、关系和推理步骤。

过程经验可以较积极地跨 bot 泛化，例如风控口径必须统一、恢复风险需要持续确认。市场经验受 Regime 和 persona 影响更大，只能作为带分布和反例的假设，不能直接作为仓位指令。

图书馆可能间接改善收益，但也可能因为错误召回、过度保守或僵化规则降低收益。因此，收益改善必须由样本外实验验证，不能从卡片数量、关系数量或 Agent 的文字评价推断。

### 10.3 必须进行的对照实验

至少设置五组：

| 组别 | Agent 可见内容 | 用途 |
|---|---|---|
| A | 不使用图书馆 | 原始基线 |
| B | 只看相似案例 | 判断普通案例检索是否已经足够 |
| C | 使用经验卡，但不提供六种关系 | 判断结构化经验卡本身的贡献 |
| D | 使用完整图书馆、反例和关系导航 | 测量完整系统效果 |
| E | 使用被随机打乱的关系 | 负向对照，识别关系层是否真的有用 |

实验必须按时间滚动，只允许读取决策日当时已经可见的 Snapshot 和结果；禁止同一 run、同一未来区间回流。不同组使用相同模型、提示词、行情输入、交易成本和随机种子。

核心指标包括：

- 图书馆召回后，Agent 是否实际改变了决策；
- 改变决策后的超额收益、最大回撤和风险调整收益；
- 换手率、交易成本和规则违规次数；
- 同类失效模式是否重复发生；
- 各种关系分别触发多少次、被采用多少次、采用后的结果如何；
- `not_applicable` 和 `uncertain` 比例，用于识别召回是否过宽。

只有完整系统 D 在严格样本外稳定优于 A、B、C，并且打乱关系的 E 明显变差，才能说明关系图书馆本身产生了增量价值。

最终判断标准是：**这套系统值得建设，但第一目标是提高决策质量和风险控制；能否产生投资 Alpha，必须由无未来信息的样本外对照实验回答。**

## 11. PIT 经验与版本管理

### 11.1 PIT 是查询语义，不是每日复制

不要为每个交易日复制一套经验卡或数据库。经验只保存不可变版本和时间事件；PIT 通过 `as-of` 查询重建某一时点真实可见的知识。

每个对象至少区分三个时间：

| 时间 | 含义 |
|---|---|
| `event_at` | 事情实际发生的时间 |
| `available_at` | 系统最早能够知道该事实或结果的时间 |
| `published_at` | 内容完成整理、校验和裁决，正式进入馆藏的时间 |

例如，8月10日发生的决策，其 D+20 结果可能到9月7日才完整可见，经验到9月8日才通过校验发布。描述对象虽然发生在8月10日，但该后验经验不能出现在8月10日的回测中。

经验的可见时间必须满足：

```text
published_at >= 所有输入事实的 available_at
published_at >= 所有已引用结果的 outcome_available_at
```

结果尚未成熟时，可以发布只含当时事实的 L1 Candidate，但不能把尚不可见的结果写成支持证据。

### 11.2 PIT 构建流程

在截止时间 T，只允许执行：

```text
读取 available_at <= T 的事实
        ↓
生成当时能够构建的 Canonical 案例
        ↓
提炼 Candidate 经验
        ↓
只挂接 available_at <= T 的证据与关系
        ↓
使用 T 时点有效的裁决规则确定等级
        ↓
校验完成后，以 published_at 纳入馆藏 Snapshot
```

原始文件修改时间不能充当 `available_at`。如果无法证明某项数据在 T 时点已经可得，应当 fail closed：不向 Agent 提供。

### 11.3 内容、证据和状态分别版本化

新增证据不应复制整张经验卡。三类变化分别管理：

1. **内容版本**：Claim、适用条件、作用机制、失效边界或证伪条件变化时，产生新的 `content_version`；
2. **证据事件**：新增支持、反驳或未决证据时，追加 `evidence_event`；
3. **裁决事件**：晋升、降级、废止或恢复时，追加 `adjudication_event`。

例如：

```text
exp_001 / content_version=1
08-10  L1 Candidate
09-07  新增 SUPPORTS 证据
09-08  晋升 L2
10-15  新增 REFUTES 证据
10-16  收窄适用范围，产生 content_version=2
```

查询8月20日应看到 v1、L1；查询9月20日应看到 v1、L2；查询10月20日应看到 v2。旧版本和旧状态永远保留，不能覆盖修改。

同样地，六种推理关系也要保存 `known_from / known_to` 或等价的关系版本。后来发现的冲突、泛化或优先关系，不能回填到它尚未被认识的历史日期。

### 11.4 最小 PIT 数据结构

- `experience_cards`：稳定的经验身份 `card_id`；
- `experience_card_versions`：不可修改的内容版本及来源清单；
- `evidence_events`：证据结论、来源案例和 `available_at`；
- `relation_versions`：六种关系及其可见时间、有效时间和判据；
- `adjudication_events`：状态变化、裁决规则版本和审批记录；
- `library_snapshots`：`knowledge_cutoff`、策略版本和 manifest hash；
- `snapshot_entries`：Snapshot 包含的卡片版本和当时状态；
- `usage_logs`：Agent 在哪个 Snapshot 下使用了什么经验。

Snapshot 只保存 ID、版本和状态清单，不复制卡片全文，因此不会因每日回测产生大量重复数据。只有馆藏发布变化或新 run 需要冻结知识边界时才创建 Snapshot。

### 11.5 Agent 的唯一访问入口

Agent 不直接查询底层版本表，只能调用：

```text
library_as_of(decision_time, consumer_bot, consumer_run)
```

服务端统一完成：

- 只返回 `published_at <= decision_time` 的经验；
- 只返回 `available_at <= decision_time` 的事实和证据；
- 锁定当时可见的卡片与关系版本；
- 隐藏后来产生的裁决、后验结果和关系；
- 排除同一 run 或重叠时期的自我泄漏；
- 记录本次查询使用的 Snapshot ID 和 manifest hash。

Qwen 负责语义整理，Agent 负责推理，但两者都不能自行决定时间可见性或修改历史版本。PIT、版本选择和泄漏检查必须由确定性程序执行。

最终原则是：**经验内容、证据变化和状态变化分别管理；所有变化只追加、不覆盖；PIT 依靠 as-of 查询重建，而不是复制每日数据库。**

## 12. Agent 运行时使用协议

### 12.1 不是“六选一后再看案例”

Agent 不直接扫描图书馆，也不是先在六种关系中盲选一条。正确流程是：系统先机械匹配少量种子经验，并同时提供最低限度的正反证据；Agent 理解初始争议后，再决定是否沿某种关系继续调查。

```text
当前处境
   ↓ 系统机械匹配
种子经验卡（通常 1～3 张）
   ↓
最小证据包
   ├─ 一个代表性支持案例
   ├─ 一个最强反例或 Regime 警报
   ├─ 一个不同动作的对照案例
   └─ 相关的冲突或优先经验
   ↓
Agent 判断哪些分支值得继续
   ↓
沿指定关系追加查询
   ↓
综合证据，形成自己的判断
```

如果让 Agent 在看见反证之前自由选边，已经倾向某个动作的 Agent 很可能只选择 `CORROBORATES`。因此，最强反例或冲突经验必须由系统强制放入初始证据包。

### 12.2 六种关系分别返回什么

| 调查方向 | 返回对象 |
|---|---|
| `CORROBORATES` | 支持该经验的聚合证据和代表案例 |
| `REGIME_ALERT` | 相同处境、相同动作但结果相反的案例 |
| `CONTRASTS` | 相同处境下采取不同动作的案例 |
| `GENERALIZES / SPECIALIZES` | 更一般或更具体的经验卡 |
| `CONFLICTS_WITH` | 提出相反建议的经验卡及双方证据 |
| `DEPENDS_ON / OVERRIDES` | 前置条件或拥有更高优先级的经验、规则 |

前三类主要通向案例或证据集合，后三类主要通向其他经验卡。Agent 看到的是聚合统计和少量代表案例，不是全部底层证据行。

### 12.3 Agent 必须提交的判断

Agent 使用经验后至少要回答：

1. 该经验对当前处境是 `applicable`、`not_applicable` 还是 `uncertain`；
2. 当前处境与来源案例最重要的差异是什么；
3. 最强反例是否足以推翻该经验；
4. 不同动作的对照提供了什么信息；
5. 是否存在更高优先级的规则或硬约束；
6. 最终采用、修改还是拒绝该经验；
7. 什么条件出现时，本次判断失效。

图书馆提供线索和张力，Agent 负责综合判断，不能照抄案例动作。

### 12.4 第一版：预编译一跳简报

第一版不直接实现无限多轮图遍历。系统在一个 Prompt 中为每张种子经验预编译：

```text
经验主张
匹配原因
适用与失效边界
支持案例摘要
最强反例摘要
动作对照摘要
冲突或优先规则
```

先验证 Agent 是否会认真比较、能否识别差异，以及经验是否真实改变决策。如果一跳简报只产生套话，增加更多图遍历只会放大成本和噪声。

### 12.5 后续版本：带类型的关系导航

第一版验证有效后，再提供受控工具：

```text
walk(from_id, relation_type, as_of, limit)
```

例如：

```text
walk(exp_001, REGIME_ALERT, 2026-10-20, 3)
```

服务端按照 PIT 规则返回最多三个当时可见的反向案例。每次调用记录起点、关系类型、返回对象、Agent 判断和支线结论，并设置总步数和 token 预算。

最终分工是：**环境负责想起来并强制提供最低限度的正反证据；Agent 负责沿有价值的关系继续调查并想明白；协议负责让整个过程可检查、可回放。**
